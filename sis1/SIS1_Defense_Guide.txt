1. АРХИТЕКТУРА И СТРУКТУРА ПРОЕКТА
--------------------------------------------------------------------------------
Проект построен по принципам классической промышленной многослойной архитектуры:

  [Client: requests.http]
           │
           ▼ HTTP (JSON)
  [web: Controllers]       - Принимает HTTP, отдает статусы (200, 201+Location, 204)
           │ Request/Response DTO + @Valid
           ▼
  [service: Services]      - Бизнес-логика, проверка остатков склада, дубликатов
           │ Domain Models
           ▼
  [repository: Interfaces] - Абстракция доступа к данным (DIP из SOLID)
           │
           ▼
  [repository: InMemory]   - Хранилище в памяти на ConcurrentHashMap и AtomicLong

Дополнительные слои:
- config:    типобезопасная привязка настроек @ConfigurationProperties (AppProperties)
- exception: глобальный перехватчик @RestControllerAdvice и формат ApiErrorResponse

2. ЗАЩИТА ВСЕХ 6 ПУНКТОВ ЧЕК-ЛИСТА
--------------------------------------------------------------------------------

ПУНКТ 1: CRUD эндпоинты через DTO (Request / Response DTOs)
-----------------------------------------------------------
* Сущности: Category, Product, Order.
* Для каждого ресурса созданы отдельные DTO на базе Java record:
  - CategoryRequest, CategoryResponse
  - ProductRequest, ProductResponse
  - OrderRequest, OrderStatusUpdateRequest, OrderItemResponse, OrderResponse
* Зачем DTO: Разделяет внешний контракт API и внутренние модели базы. Клиент не
  может подменить ID или дату создания (их генерирует сервер), а в Response DTO
  мы добавляем вычисляемые поля (например, categoryName вместо categoryId).

ПУНКТ 2: Bean Validation (@Valid на каждом теле запроса)
-------------------------------------------------------
* Декларативная валидация входящих данных через аннотации Jakarta Validation:
  - @NotBlank, @Size(min=2, max=60) — обязательные непустые строки (имя, категория).
  - @Pattern(regexp = "^[A-Z0-9-]{3,20}$") — проверка формата артикула SKU.
  - @Positive — цена строго больше 0.
  - @PositiveOrZero — остаток на складе не может быть отрицательным.
  - @Email — валидация email покупателя при оформлении заказа.
  - List<@Valid OrderItemRequest> — каскадная валидация каждого элемента списка!
* В контроллерах перед каждым телом запроса стоит @Valid @RequestBody.

ПУНКТ 3: Unified Error Format (Единый формат ошибок via @RestControllerAdvice)
-----------------------------------------------------------------------------
* Класс GlobalExceptionHandler с аннотацией @RestControllerAdvice ловит все сбои.
* Любая ошибка на сервере возвращает стандартизированный JSON (ApiErrorResponse):
  {
    "timestamp": "2026-10-04T18:00:00Z",
    "status": 400,
    "error": "Bad Request",
    "message": "Request validation failed",
    "path": "/api/v1/products",
    "fieldErrors": {
      "price": "Price must be greater than 0",
      "sku": "SKU must match pattern ^[A-Z0-9-]{3,20}$"
    }
  }

ПУНКТ 4: Правильные HTTP статус-коды (Correct status codes)
----------------------------------------------------------
* 200 OK — успешное получение (GET) или обновление (PUT).
* 201 Created + Location header — успешное создание (POST).
  Заголовок Location формируется динамически:
  ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(...)
* 204 No Content — успешное удаление (DELETE) с пустым телом ответа.
* 400 Bad Request — ошибки валидации @Valid или неверный формат параметров.
* 404 Not Found — сущность с таким ID не существует (ResourceNotFoundException).
* 409 Conflict — логические конфликты бизнес-правил (ResourceConflictException):
  1) Дубликат имени категории;
  2) Дубликат артикула товара (SKU);
  3) Удаление категории, в которой еще есть товары;
  4) Нехватка товара на складе при попытке оформить заказ;
  5) Изменение статуса уже доставленного или отмененного заказа.

ПУНКТ 5: Maven build with profiles (dev и test профили)
-------------------------------------------------------
* В pom.xml настроены два профиля сборки:
  - dev (активен по умолчанию) -> порт 8080, pageSize=50, логи DEBUG.
  - test -> порт 8081, pageSize=10, smsEnabled=true.
* Параметры считываются классом AppProperties (@ConfigurationProperties).
* StartupLogger при старте выводит в консоль активный профиль и параметры.
* Контроллер ConfigController (/api/v1/config) позволяет проверить профиль по HTTP.

ПУНКТ 6: HTTP-client collection (requests.http)
-----------------------------------------------
* Файл requests.http в корне проекта содержит 28 готовых запросов.
* Запускается кликом по зеленым стрелкам Play прямо внутри IntelliJ IDEA.
* Покрывает все 3 ресурса: положительные сценарии и все возможные ошибки.

3. ТОП-7 ВОПРОСОВ ПРЕПОДАВАТЕЛЯ И ИДЕАЛЬНЫЕ ОТВЕТЫ
--------------------------------------------------------------------------------

Вопрос 1: Почему вы сделали интерфейсы репозиториев, если база в памяти?
Ответ:    Это принцип инверсии зависимостей (DIP из SOLID). В силлабусе указано,
          что на 5-6 неделях мы заменим память на PostgreSQL и Flyway.
          Благодаря интерфейсам, мы просто подключим Spring Data JPA к базе,
          а сервисы, контроллеры и DTO не изменятся ни на одну строчку.

Вопрос 2: Почему для денег используется BigDecimal, а не double или float?
Ответ:    Типы с плавающей точкой хранятся в двоичном виде приближенно, из-за чего
          возникают ошибки округления (0.1 + 0.2 = 0.30000000000000004).
          В онлайн-магазинах потеря денег недопустима, поэтому стандарт для
          финансовых расчетов — класс точной арифметики BigDecimal.

Вопрос 3: Зачем нужны ConcurrentHashMap и AtomicLong в репозиториях?
Ответ:    Веб-сервер обрабатывает каждый HTTP-запрос в отдельном потоке. Обычный
          HashMap в многопоточной среде может сломаться или зациклиться.
          ConcurrentHashMap потокобезопасен. А AtomicLong гарантирует уникальные
          ID без гонок потоков через процессорные инструкции CAS (Compare-And-Swap).

Вопрос 4: Как работает каскадная валидация списка позиций в заказе?
Ответ:    В OrderRequest поле объявлено как List<@Valid OrderItemRequest> items.
          Аннотация @Valid перед типом заставляет Spring валидировать каждый объект
          внутри списка (чтобы количество было >= 1 и был указан productId).

Вопрос 5: В каких случаях API возвращает статус 409 Conflict?
Ответ:    При нарушении бизнес-правил: дубликат SKU товара, дубликат имени
          категории, удаление непустой категории, заказ товара при нехватке остатка
          на складе или попытка изменить уже завершенный заказ.

Вопрос 6: Зачем нужен заголовок Location при статусе 201 Created?
Ответ:    По спецификации RFC 7231 и REST-стандартам, при создании нового ресурса
          сервер обязан вернуть URL, по которому этот ресурс теперь доступен.
          Мы формируем его через ServletUriComponentsBuilder.

Вопрос 7: Как устроен глобальный обработчик ошибок?
Ответ:    Класс с аннотацией @RestControllerAdvice перехватывает исключения со всех
          контроллеров. Методы с @ExceptionHandler ловят конкретные типы ошибок и
          возвращают единый предсказуемый JSON-объект ApiErrorResponse.
