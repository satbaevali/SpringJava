1. Архитектура и структура проекта

Проект построен по стандартам промышленной многослойной архитектуры (Layered Architecture):

  • config — привязка типобезопасных настроек через @ConfigurationProperties (класс AppProperties) и стартовый логгер StartupLogger.
  • model — чистые доменные сущности (Category, Product, Order, OrderItem, OrderStatus).
  • repository — абстракция доступа к данным: интерфейсы + потокобезопасная In-Memory реализация на ConcurrentHashMap и AtomicLong.
  • dto — объекты передачи данных (Request / Response DTO на базе Java record) с аннотациями Bean Validation.
  • exception — перехватчик исключений @RestControllerAdvice и единый формат ошибок ApiErrorResponse.
  • service — изолированная бизнес-логика (списание остатков со склада, подсчет чека, проверка дубликатов).
  • web — REST-контроллеры, возвращающие корректные HTTP статус-коды (201 + Location, 200, 204).

3. Топ-7 вопросов преподавателя и идеальные ответы

1. Почему вы использовали интерфейсы для репозиториев, если сейчас всё хранится в памяти?

Ответ: Это принцип инверсии зависимостей (DIP из SOLID). В силлабусе указано, что на 5–6 неделях мы заменим память на PostgreSQL и Flyway. Благодаря интерфейсам CategoryRepository, ProductRepository и OrderRepository, нам потребуется только подключить Spring Data JPA к базе данных, а контроллеры, DTO и сервисы не изменятся ни на одну строчку.

2. Почему для цен и денежных расчетов используется BigDecimal, а не double или float?

Ответ: Типы double и float используют двоичное представление с плавающей точкой, из-за чего возникают погрешности округления (например, 0.1 + 0.2 дает 0.30000000000000004). В e-commerce и финансовом секторе это приводит к ошибкам в балансах и чеках, поэтому стандарт для денег в Java — это класс точной десятичной арифметики BigDecimal.

3. Зачем в репозитории применены ConcurrentHashMap и AtomicLong вместо обычных HashMap и long?

Ответ: Веб-сервер Spring Boot обрабатывает каждый HTTP-запрос в отдельном потоке пула Tomcat. Обычный HashMap в многопоточной среде может повредить внутреннюю структуру или зациклиться. ConcurrentHashMap гарантирует потокобезопасность. А AtomicLong выполняет потокобезопасный инкремент ID через процессорную операцию CAS (Compare-And-Swap), исключая дубликаты ID при параллельных запросах.

4. Что такое каскадная валидация в OrderRequest?

Ответ: В классе OrderRequest поле позиций заказа объявлено как List<@Valid OrderItemRequest> items. Аннотация @Valid перед типом элемента указывает Спрингу валидировать каждый объект внутри списка. Если у хотя бы одного товара количество меньше 1 или не указан productId, запрос будет отклонен с 400 Bad Request.

5. В каких случаях ваш API возвращает 409 Conflict?

Ответ: Статус 409 Conflict возвращается при нарушении бизнес-правил согласованности данных:
1) Попытка создать категорию с уже существующим именем;
2) Попытка создать товар с дублирующимся артикулом (SKU);
3) Попытка удалить категорию, в которой еще есть товары;
4) Попытка заказать товара больше, чем фактически имеется на складе;
5) Попытка изменить статус уже доставленного (DELIVERED) или отмененного заказа.

6. Зачем нужен заголовок Location при статусе 201 Created?

Ответ: По спецификации RFC 7231 и стандарту REST, при успешном создании нового ресурса сервер обязан вернуть не только статус 201, но и ссылку (URI), по которой клиент может сразу запросить этот созданный ресурс. Мы формируем его динамически через ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(created.id()).toUri().

7. Как устроен единый формат ошибок через @RestControllerAdvice?

Ответ: Аннотация @RestControllerAdvice делает класс глобальным перехватчиком исключений для всех контроллеров проекта. Методы с аннотацией @ExceptionHandler ловят конкретные ошибки (MethodArgumentNotValidException, ResourceNotFoundException, ResourceConflictException) и оборачивают их в единый рекорд ApiErrorResponse с полями timestamp, status, error, message, path и картой полей с ошибками fieldErrors.

4. 3-минутный сценарий живой демонстрации на защите

  1. Шаг 1 (Запуск): Запустите Sis1Application. Обратите внимание преподавателя на лог консоли:
    >>> Активные профили: [dev] | app.name='Online Store API (DEV)' | app.pageSize=50 <<<
    (Показывает выполнение пункта 5 о профилях).
  2. Шаг 2 (Успешные операции): Откройте файл requests.http в IntelliJ IDEA. Нажмите зеленую кнопку ▶ на запросе 1.4 [POST] Create category.
    Покажите, что ответ вернул 201 Created, и в заголовках ответа появился Location: http://localhost:8080/api/v1/categories/4.
  3. Шаг 3 (Валидация Bean Validation): Выполните запрос 2.6 [POST] Create product with invalid fields.
    Покажите ответ 400 Bad Request и единый JSON со списком некорректных полей:
    {"sku": "SKU must match pattern...", "price": "Price must be greater than 0"}.
  4. Шаг 4 (Бизнес-конфликты 409): Выполните запрос 1.8 Delete category with products (попытка удалить категорию Laptops с товарами).
    Покажите статус 409 Conflict: «Cannot delete category with id=1 because it still contains products».
  5. Шаг 5 (Работа со складом при заказе): Выполните запрос 3.6 Create order with insufficient stock (заказ 95 макбуков при остатке 10).
    Покажите статус 409 Conflict с точным сообщением о нехватке остатков.
  6. Шаг 6 (Удаление): Выполните запрос 1.9 Delete empty category.
    Покажите статус 204 No Content с пустым телом ответа.
